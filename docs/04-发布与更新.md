# 04 · 开源发布与版本更新

本手册是任务工作台的发布入口，适合日常交给 Agent 执行，也可由维护者自己操作。它覆盖组织仓库、npm 和两个插件索引；测试细则见 [05 协作与测试](./05-协作与测试.md)。

## 1. 先了解几个地方

| 地方 | 做什么 | 任务工作台的位置 |
|---|---|---|
| GitHub 组织仓库 | 保存源码、文档、版本标签和 Release | [Zevin-Labs/task-workbench](https://github.com/Zevin-Labs/task-workbench) |
| npm | 发布安装包；从 npm 安装的用户通过新版本获取更新 | [dsh-task-workbench](https://www.npmjs.com/package/dsh-task-workbench) |
| dshfind | 按其规则发现 GitHub 和 npm 中的插件，生成插件索引 | [dshfind 索引](https://api.dshfind.com/market/dsh-index.json) |
| Awesome DSH Plugin | 通过社区仓库的 PR 收录插件，并自动生成插件索引 | [社区目录](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin)、[索引镜像](https://cdn.jsdelivr.net/npm/dsh-plugin-catalog/index.json) |

**commit 是保存在本机；push 是上传 GitHub；npm publish 是发布安装包。** 插件市场索引有各自的同步与审核，不保证跟 GitHub 或 npm 同时更新。

GitHub 组织仓库只是仓库的归属不同，操作方式与个人仓库相同。此项目的 `origin` 指向组织仓库；另一个 `archive` 远程是旧项目归档，日常发布不用它。

## 2. 应该做哪种操作

| 改动 | 操作 | 效果 |
|---|---|---|
| 还在开发或只自己使用 | 测试后本地 commit | 本机保存，不影响线上用户 |
| 只更新源码说明、文档、协作规则或 CI | commit，按需 push GitHub | 更新仓库；通常无需发 npm |
| 功能、修复、技能或插件包配置需要给用户使用 | 完整发版 | 测试、升版本、推 GitHub、发 npm、创建 Release，再核对市场 |

`README` 和 `LICENSE` 也会进入 npm 包。单独修改时通常可等下一次功能发版同步；若要立刻更新 npm 页面，则需要发布新版本。只推 GitHub 不会自动更新 npm 包。

Agent 默认仅做本地提交；**每次 GitHub 推送、npm 发布、GitHub Release 和市场投稿都需要仓库所有者明确授权**。一次明确授权的完整发版包含这次发版的 GitHub、npm 和 Release；修改其他仓库的市场 PR 也应在授权范围内。不要因为存在脚本而自动执行外部发布。

## 3. 发版前准备

1. 确认这次改了什么，完成相关功能的人工检查；涉及数据结构或不兼容行为时，在发布说明中讲清楚对已有用户的影响。
2. 在项目目录运行 `git status --short --branch`，检查待提交的文件。只提交属于本次发布且已确认的改动；个人数据库、设置、token 和本机路径不能提交。
3. 确认处于 `main` 或 `master`，需要发布的改动已经提交，工作区干净。脚本不会替你整理或提交未提交的业务改动。
4. 确认 GitHub 和 npm 权限：`gh auth status`、`npm whoami`。npm 没有登录时执行 `npm login`，在自己的浏览器完成登录。GitHub 应有组织仓库写入权限，npm 账号应有该包的发布权限。
5. 决定版本号。一般修复用 `patch`，新功能用 `minor`；不兼容变化需明确记录，处于 `0.x` 阶段时可根据项目约定升 minor，不要把它当成普通 patch。已发布的 npm 同名同版本无法覆盖或重复使用。

脚本会运行一次 `npm run verify` 和 `npm run pack:check`：前者做语法及全量测试，后者检查包内必需文件和禁止打包的目录。不要在同一次发版中无故重复全量测试。根据 [项目测试纪律](./05-协作与测试.md)，自动化测试只使用临时数据根，不能接触真实数据。

## 4. 完整发版

在仓库根目录执行：

```sh
npm run release -- minor --dry-run  # 预演，只打印步骤，不执行发布
npm run release -- minor            # 确认后执行；也可用 patch 或指定版本号
```

不指定版本类型时脚本会询问。`--dry-run` 仍要求在 `main`/`master` 且工作区干净；它不会验证实际权限或完成任何发布。脚本执行顺序：

1. 检查 npm 登录、测试和打包。
2. 用 `npm version` 修改版本，生成本地版本提交和 tag。
3. 将当前分支和关联 tag 推送到 `origin`。
4. 执行 `npm publish`，按 npm 提示完成浏览器验证或认证器验证。
5. 如果安装了 `gh`，打包并创建 GitHub Release；没有 `gh` 时脚本提示跳过该步骤，需要另行创建。Release 可附带生成的安装包和发布说明。

npm 可能在发布时给出一次性浏览器验证链接。及时打开并完成验证；如果网页提示令牌无效或过期，先查看发布命令是否仍在运行，不要把这与已有的 npm access token 直接等同。发布认证信息、密码和验证码不要放进仓库或聊天。

脚本按步骤执行，**不是跨 GitHub 和 npm 的原子事务**。任何一步失败都不会自动撤销前面已经完成的步骤。不要在失败后直接再次执行整个脚本或再次升版本，先按第 6 节检查实际状态。

## 5. 发布后检查两个索引

先核对代码和安装包：

```sh
git status --short --branch
npm view dsh-task-workbench version dist-tags --json --prefer-online
gh release view v<版本号> --repo Zevin-Labs/task-workbench
```

上面 `v<版本号>` 是占位写法，执行时替换为实际 tag，例如 `v0.6.0`。npm 返回发布成功后可能还需处理一段时间，公开查询未更新时稍后再查；不应立即重复发布。按 [05 的发版验收](./05-协作与测试.md)检查 npm 安装路径，真实数据检查须先备份并在验收后恢复。

### 5.1 dshfind

- [索引地址](https://api.dshfind.com/market/dsh-index.json)。dshfind 说明其从公开 GitHub 仓库的 `dsh-plugin` topic 定期发现插件；该索引的说明还要求 npm 包与 GitHub 仓库关联。项目已有该 topic，npm 的 `repository` 指向项目仓库。
- 无需为每次更新提 PR。同步后在索引或 dshfind 页面搜索 `dsh-task-workbench` / `task-workbench`，核对是否出现及版本是否更新。
- 首次收录若经过两个同步周期仍未出现，按 [dshfind 投稿说明](https://github.com/hikariming/dshfind#submit-your-plugin)向其反馈；自动发现不保证最终收录。

### 5.2 Awesome DSH Plugin / jsDelivr

- [索引地址](https://cdn.jsdelivr.net/npm/dsh-plugin-catalog/index.json)由 Awesome DSH Plugin 社区目录生成并发布，不是单独的投稿入口。参见 [目录包说明](https://www.npmjs.com/package/dsh-plugin-catalog)。
- 首次收录申请是 [PR #12498](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/pull/12498)。**以 PR 页面显示的状态为准**：检查通过不等于已经合并，合并后也需要等待索引构建和 CDN 更新。
- 插件目录的条目是上游仓库 `data/plugins/Zevin-Labs__task-workbench.yml`。如果现有收录 PR 仍开放，就在该 PR 对应分支更新条目；如果已合并，以社区仓库最新主分支为基础修改该文件并新建 PR。遵循当时的[投稿规则](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/blob/main/contributing.md)，不要手工修改自动生成的 README。
- 条目当前含固定版本的 `tarball` 链接。每次发版后检查它是否仍指向旧 Release；希望备用安装包同步新版本时，在已创建且可访问的新 Release 基础上更新链接并提交市场 PR。**更新 npm 不会自动改这个固定链接。** 插件改名、仓库地址、描述、图标或分类变化时也检查条目。
- 已开放 PR 可在页面查看检查状态。因仓库创建时间不够而失败时，仓库达到条件后社区的定时任务会尝试重新检查；检查时间和合并由社区决定，不能保证立即变绿。

## 6. 失败后怎么继续

先记录失败在哪一步，并分别检查本地 `package.json` 版本、`git status`、远程 tag、npm 和 GitHub Release。不要强制推送、删除 tag 或撤销已发布的包来重试。

| 情况 | 怎么处理 |
|---|---|
| 检查或打包失败，尚未升版本 | 修好问题并运行受影响的检查，再按实际状态继续；如果重新开始完整发版，按测试纪律决定是否需再跑全量。 |
| 已生成本地版本提交和 tag，但 GitHub 推送失败 | 检查 `origin`、权限及远程分支，确认无冲突后推送已有提交和 tag；不要再次执行 `npm version`。 |
| GitHub 已推送，npm 登录或验证失败 | 确认 npm 上该版本尚不存在；重新登录或重新发起发布认证，然后在对应版本提交上执行 `npm publish`。临时网页验证链接过期时，新的发布尝试会生成新链接。 |
| npm 命令返回成功，但查询仍是旧版 | 给 registry 处理及缓存刷新时间，稍后用 `npm view ... --prefer-online` 再查；不要重复发布同版本。 |
| npm 成功，但 GitHub Release 失败或跳过 | 保留现有版本和 tag；确认 tag 已推送，再通过 GitHub 页面或 `gh release create` 为现有 tag 建立 Release，按需附上用 `npm pack` 生成的安装包。 |
| 市场申请仍在等待或失败 | 查看 PR 的最新检查结果与反馈，区分仓库年龄、数据格式或其他问题；只处理实际发现的问题。市场 PR 不是 npm 发布的前提。 |

## 7. 项目标识与历史

- 组织仓库：`Zevin-Labs/task-workbench`；npm 包：`dsh-task-workbench`。
- `0.5.0` 使用 Markdown；`0.6.0` 使用 SQLite，不自动导入旧版 Markdown。版本历史以 [GitHub Releases](https://github.com/Zevin-Labs/task-workbench/releases) 和 [npm](https://www.npmjs.com/package/dsh-task-workbench) 的实时状态为准。
- 个人账户及未来其他插件可以参考本手册，但各自的 GitHub 仓库、npm 包名、权限、市场条目和收录状态需要单独确认，不要照搬本项目标识。
