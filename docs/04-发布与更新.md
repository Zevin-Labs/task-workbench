# 04 · 开源发布与版本更新

> 面向「不写代码但要维护这个插件」的所有者，以及未来的维护者。
> 只回答一件事：**改了代码之后，怎么让用户拿到新版本**。
> 当前版本：`0.3.0`；首次发布流程已完成，本文记录的是日常更新流程。

## 0. 先分清两种操作

| 场景 | 要发版吗 | 测试 | Git / npm |
|---|---|---|---|
| 平时自用，改完即用 | 否 | 只跑对应域的定向测试（[05 协作与测试](./05-协作与测试.md) §3） | 本地 `git commit`，**不 push** |
| 攒了一批用户可感知的修复/改动 | 是 | 发版前全量一次 `npm run verify` | 升版本 → `git push --follow-tags` → `npm publish` → GitHub Release |

**是否要发版的判据**：只有 `lib/`、`skills/`、`locale/`、`icon.svg`、`cordis.patch.yml`、`package.json` 的分发字段变化才需要发版（用户装的是 npm 包）；只改 `docs/`、`AGENTS.md`、`CONTRIBUTING.md`、CI 不需要发版，GitHub 更新即可；README / LICENSE 改动一般也不用，想让 npm 页面同步就随下次发版。

## 1. 三个地方各是什么

| 地方 | 角色 | 地址 |
|---|---|---|
| **GitHub** | 源代码仓库：代码、文档、Issue、Release | https://github.com/Zevin-Labs/personal-task-workbench |
| **npm** | 软件分发仓库：`dsh plugin add` 从这里下载，市场也优先读它 | https://www.npmjs.com/package/dsh-personal-task-workbench |
| **插件市场** | 展示与收录：awesome 列表 → dshmarket / 官方「发现」索引 | `awesome-dsh-plugin` 仓库里的一个 YAML |

一句话：**GitHub 是源头，npm 是货架，市场是广告牌。** 用户安装走的是 npm（或 GitHub 源码 / Release tarball）；市场只负责让人找到它。

## 2. 改了代码之后：一次完整发版

> 下面命令都在仓库目录执行：`cd ~/LocalApps/personal-task-workbench`

## 2.0 最简方式：一条命令（推荐）

```sh
npm run release
```

脚本 `scripts/release.sh` 会依次做：测试 → 升版本 → 推 GitHub → 提示粘贴 token → 发布 npm → 建 GitHub Release。
中途任何一步失败都会停下；工作区不干净、不是 main 分支、测试不过，都不会继续。

常用参数：

```sh
npm run release -- patch          # 直接指定 patch（修 bug）
npm run release -- minor --yes    # 加功能，不再确认
npm run release -- --dry-run      # 只打印步骤，不改任何东西（可先跑一次看流程）
```

> 脚本在 `main` 分支、工作区干净时才工作。token 仍然需要你手动创建并粘贴（见 §2.4）。

### 2.1 先测试（发版门禁）

```sh
npm run verify   # 语法检查 + 全部 89 个用例
```

必须全部通过再发版。日常小改动不要跑全量，按 [05 协作与测试](./05-协作与测试.md) §3 跑对应域的定向测试即可。

### 2.2 升版本号（三选一）

遵循语义化版本：

| 改了什么 | 版本怎么升 | 例子 |
|---|---|---|
| 修 bug、改文案 | patch | `0.3.0` → `0.3.1` |
| 加功能、加字段 | minor | `0.3.1` → `0.4.0` |
| 不兼容的大改 | major | `0.x` 阶段一般不用 |

```sh
npm version patch -m "release: v%s"   # 自动改 package.json + 本地提交 + 打 tag v0.3.1
```

### 2.3 推到 GitHub

```sh
git push origin main --follow-tags
```

### 2.4 发布到 npm

npm 账号开了 2FA（passkey）。发布时用下面任一方式完成 2FA：

**方式 A：临时 token（推荐，最省心）**

1. 打开 https://www.npmjs.com/settings/zevin-labs/tokens
2. Generate New Token → **Granular Access Token**
3. Token name 随意；Permissions 选 **Read and write**；Packages 选 **All packages**；勾上 **Bypass two-factor authentication (2FA)**；有效期选 1 天
4. 生成后复制 `npm_...`，然后执行：

```sh
printf "npm token: "; read -s NPM_TOKEN; echo
npm publish --//registry.npmjs.org/:_authToken="$NPM_TOKEN"
unset NPM_TOKEN
```

5. 回 tokens 页面把 token 删掉。

**方式 B：账号同时配置了认证器（TOTP）时**

```sh
npm publish --otp=认证器里的6位码
```

注意：发布 token 只用于发布，**不要写进仓库、不要发聊天、不要提交到 Git**。

### 2.5 建 GitHub Release（建议，不强制）

```sh
npm pack
gh release create v0.3.1 dsh-personal-task-workbench-0.3.1.tgz \
  -R Zevin-Labs/personal-task-workbench \
  --title "v0.3.1" --notes "修了什么写在这里"
rm -f *.tgz
```

Release 是给不用 npm 的人准备的兜底安装包；市场条目的 `tarball:` 字段当前指向 v0.3.0，**建议每次发版顺手改成最新版**（否则从市场走的兜底安装会停在旧版）；npm 主路径不受影响。

### 2.6 市场要不要动？

**一般不用。** 列表条目只记录仓库地址和描述；版本、下载量由市场从 npm 自动读。dshmarket 发现 npm 有新版本会提示更新。

只有这些情况才需要改市场条目（向 `awesome-dsh-plugin` 提 PR）：
- 插件改名 / 换仓库地址
- 描述、图标需要更新
- 分类放错了

## 3. 常见报错对照

| 报错 | 原因 | 处理 |
|---|---|---|
| `E403 ... Two-factor authentication ... required` | 没带 OTP，或 token 没勾 Bypass 2FA | 用方式 A/B 重来 |
| `EOTP` | 6 位码过期（30 秒） | 等下一个码重新执行 |
| `ENEEDAUTH` | token 为空 / 没登录 / `read` 失败 | 确认 `read -s` 读到了值；zsh 不要用 `read -p` |
| `403 Forbidden` 发布同名版本 | 这个版本号已经发过了 | 升版本号再发，不能覆盖已发布版本 |
| 市场 gate 报「repo is 0.0 days old」 | 新仓库不满 1 天 | 等 24 小时自动重跑，不用重开 PR |

## 4. 只推 GitHub、不发 npm 会怎样

- 用 `npm install` / `dsh plugin add 包名` 装过的用户：**拿不到更新**。
- dshmarket 的「有新版本」提示：**不会出现**（它比的是 npm 版本）。
- 市场条目、GitHub 源码安装：仍可工作，但用户要手动换安装方式。
- 官方「发现」索引：不会收录新版本。

结论：**发版 = GitHub + npm 都更新**。GitHub 是源头，npm 是给用户的分发渠道。

## 6. 安全底线

- token 只显示一次，用完即删；有效期越短越好。
- 不要把 token、恢复码写进仓库、文档、聊天记录。
- 发布前确认 `git status` 干净、测试全绿。
- 删除已发布版本（`npm unpublish`）只在 72 小时内且确有必要时做，发布前多检查。
