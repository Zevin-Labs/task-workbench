# 05 · 协作与测试

> 读者：首次进入本仓的智能体与日常维护者。
> 契约权威：功能见 [01](./01-功能规格.md)，SQLite 和读写实现见 [02](./02-实现架构.md)，发版见 [04](./04-发布与更新.md)。

## 1. 新智能体 10 分钟上手

### 1.1 读什么（按顺序）

1. 根 AGENTS.md：项目边界、权限与数据保护。
2. docs/README.md：当前架构与已定决策。
3. docs/01-功能规格.md：做什么与不做什么。
4. docs/02-实现架构.md：SQLite schema、事务、Service、API 与工具。
5. 本文：文件地图、测试矩阵与配置分层。

### 1.2 30 秒架构

    DSH 插件
    ├── Host lib/index.js → node:sqlite 数据库 + 三个领域 Service
    │   ├── 同源 /tw/api → UI
    │   └── 14 个 tw_* 工具 → AI
    └── Client lib/client.js → 原生 React，无构建步骤

    数据真源：默认 DSH_HOME/task-workbench/data/workbench.sqlite
    设置文件：settings.json 仅含 dataRoot 和 backupRetentionDays

- 任务、想法、复盘各有一个领域 Service；UI 和 AI 均经 Service 使用同一数据库。
- SQLite 同步短事务在一起提交业务数据、write_log 审计与域版本号。
- UI 使用 baseVersion 检查陈旧数据；AI 可不传。无文件 hash、写入队列或第二条写路径。
- 任务完成/撤销、想法状态、复盘正文只能由人操作。
- 跨月任务仍是同一条记录；过月已完成任务只读。初始化建立空数据库，不导入 0.5.0 的旧版 Markdown。

### 1.4 红线

- 不新增第二条数据库写路径；不让 AI 写人专有动作；失败必须明确。
- 自动化测试只用 os.tmpdir() 临时数据库，不碰真实数据根。
- 不提交 data/、SQLite 数据库、设置、token、个人数据或本机绝对路径。
- 临时日志、截图和探针放 test-tmp/ 或 .playwright-mcp/，交付前清理。
- 不加后台服务、ORM、配置框架或无当前需求的抽象；未来功能先确认范围。
- 文档不是验收证据；测试与真实 UI 证据分开说明。

## 2. 日常操作流程（所有者视角）

### 2.1 平时：改完就用，不发版

1. 小步改动，按 §3/§4 跑对应定向测试。
2. Host 改动重载插件；Client 改动刷新页面。
3. 本机自用可本地 commit；不 push。

### 2.2 定期：攒一批用户可感知的改动再发版

1. 发版前运行 npm run verify 与 npm run pack:check。
2. 按 [04 发布与更新](./04-发布与更新.md) 执行发布。推送、发布与 npm publish 仍须仓库所有者明确授权。
3. 是否需要发版：

| 改了什么 | 需要发版吗 | 说明 |
|---|---|---|
| docs、AGENTS.md、CONTRIBUTING.md、CI | 否 | 不进入 npm 包 |
| README、LICENSE | 通常否 | 如需同步 npm 页面随下次发版 |
| lib、skills、locale、图标、cordis.patch.yml | 是 | 会影响安装包内容 |
| package.json 的版本、engines、exports、files | 是 | 会影响分发 |

### 2.3 每天、每周不用做的事

- 日常写入不做整库备份；硬删除任务/想法和清空复盘前会创建并校验 SQLite 快照。
- 不用维护 ID 水位或独立审计日志；数据库负责 ID 与 write_log。
- backupRetentionDays 默认 7 天，可设 1–90 天。
- npm 版本只在准备发版时更新。

## 3. 测试纪律

### 3.1 分层

| 层 | 内容 | 何时跑 |
|---|---|---|
| L0 语法 | npm run check | 改 lib 后 |
| L1 定向 | 修改域测试或 settings/skills/wiring 测试 | 每次改完、交付前 |
| L2 全量 | npm test | 发版、SQLite schema/共享读写层变更、CI |
| UI 验收 | 真机重载、刷新和点击 | 改 Client 或 UI API 行为 |

### 3.2 硬规则

- 默认只跑受影响的定向测试；通过即停，不为保险扩大范围。
- 全量测试最多一次，仅用于发版、共享层或 schema 变更、CI；跑前说明影响面。
- 不重复运行未受新改动影响的全量测试。
- 自动化测试只使用 os.tmpdir()；不访问真实数据库或 DSH_HOME。

### 3.3 常用命令

    npm run check
    npm run test:task
    npm run test:idea
    npm run test:review
    npm run test:cross
    npm test

更细的单文件测试可使用 node --test tests/<file>.test.mjs。

### 3.4 覆盖边界

- tasks、ideas、reviews 的 core / Service / routes / tools 按域分层测试。
- 数据库初始化、事务、快照与设置由对应 Service/settings 测试覆盖。
- Client 没有 DOM 自动化测试；行为需在目标 DSH 界面实测。
- 未覆盖边界只在相应行为被改动或发生缺陷时补测，不为覆盖率批量加用例。

## 5. 配置文件分层

### 5.1 运行时与仓库配置（四层）

| 层 | 文件/位置 | 管什么 | 入库 | 改法 |
|---|---|---|---|---|
| L1 包与引擎 | package.json | 包名、版本、engines、exports、files、发布配置 | 是 | 分发字段变化需发版 |
| L2 插件装配 | cordis.patch.yml + package.json 的 dsh 字段 | Host / Client 如何加载 | 是 | 改装配后重载验证 |
| L3 本机运行 | DSH_HOME/task-workbench/settings.json 与独立数据根；profile 的 link: | dataRoot、backupRetentionDays、本机安装路径 | 否 | 仅改本机配置 |
| L4 协作/开发 | CI、.gitignore、AGENTS.md、CONTRIBUTING.md、docs | CI、忽略规则、Agent 边界与文档 | 是 | 按本文验收 |

### 5.2 运行时取值优先级（lib/host/settings.js）

1. DSH_HOME 环境变量决定状态目录；未设置时使用 ~/.dsh。
2. settings.json 的 dataRoot 覆盖数据库数据根；缺省为状态目录下的 task-workbench/data。相对路径按进程 cwd 解析。
3. settings.json 的 backupRetentionDays 默认 7，范围 1–90。
4. 数据库文件与 schema 决定是否已初始化；settings.json 不保存 initialized、ID 序号或 write_log 内容。
5. 不存在仓库级运行时配置，也没有第二个 dataRoot 环境变量入口。

> 本地开发可以将 `settings.json` 的 `dataRoot` 指向仓库内 `data/`（已 gitignore）。

**项目目录改名或移动时**：

1. 先关闭工作台插件，备份数据根和插件状态；确认新位置包含完整的 `workbench.sqlite` 及备份数据。
2. 检查 `$DSH_HOME/task-workbench/settings.json` 的 `dataRoot`：如指向旧项目目录，改为新数据根的绝对路径；如使用独立于项目目录的默认数据根且路径未变，无需修改。不要把本机路径提交进 Git。
3. 若插件是通过本地目录或 `link:` 安装，检查 profile 的安装链接是否指向新项目目录；必要时从新路径重新安装。npm 安装不依赖本地项目目录。
4. 重新开启插件或重启 App，使 host 重新读取设置；在工作台设置中核对数据路径，并检查原有数据。确认没有进程继续使用旧路径且旧目录没有需要保留的数据后，再自行清理旧目录。

项目目录改名不会自动更新 `dataRoot`，修改设置后也要重载插件。若仍指向旧路径，工作台可能显示未初始化或打开旧数据库；遇到空清单应先核对数据库路径和备份。

### 5.3 Agent 指令分层

- 全局 Agent 指令 → 项目 AGENTS.md → 当前任务指令；越具体越优先。
- Agent 文件只放每次都要遵守的边界；细节放本文、01 或 02，避免重复维护。

### 5.4 不要做成配置的东西

- 单用户、单数据根不需要 .env、多环境配置文件或配置加载库。
- 不将 dataRoot 做成命令行临时参数；更换时改 settings.json 后重载插件。
- 不把 token、本机绝对路径或个人数据写进仓库。

## 6. 交接与验收清单

### 6.1 每次改动完成后

- [ ] 改动在授权范围内，没有新增边界外能力。
- [ ] 记录 npm run check 和对应定向测试的命令与结果。
- [ ] Host 改动重载验证；Client 改动刷新并实测。
- [ ] 数据契约或行为变化同步更新 01/02 与相关说明。
- [ ] 状态记录只包含本次改动；按授权决定本地 commit，不 push。

### 6.2 发版额外（以 04 为准）

- [ ] npm run verify 与 npm run pack:check 通过。
- [ ] 版本按语义化规则更新；push、npm publish 和 GitHub Release 经明确授权后进行。
- [ ] 发布后使用 npm 安装路径在目标界面复验。

### 6.3 回报格式

区分已实现、已验证与未完成；列出命令和结果、未验证项及原因、是否触碰真实数据或运行进程。
