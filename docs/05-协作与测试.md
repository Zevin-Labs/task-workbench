# 05 · 协作与测试

> 读者：第一次进入本仓的智能体，以及日常维护的所有者。
> 目标：10 分钟知道「改哪里、该跑什么测试、配置动哪一层」。
> 契约权威：功能看 [01 功能规格](./01-功能规格.md)，实现与数据契约看 [02 实现架构](./02-实现架构.md)，发版看 [04 发布与更新](./04-发布与更新.md)。本文不复述细节，只给导航、纪律与配置分层。

## 1. 新智能体 10 分钟上手

### 1.1 读什么（按顺序）

1. 根 `AGENTS.md` —— 硬边界（三个域、唯一写网关、人机权限、文档极简、测试纪律、不 push）。
2. [`docs/README.md`](./README.md) —— 当前状态与已定决策（已经拍板的事不要重新讨论）。
3. [`docs/01-功能规格.md`](./01-功能规格.md) —— 做什么 / 不做什么。
4. [`docs/02-实现架构.md`](./02-实现架构.md) 的 §0–§4 —— 数据契约、双半结构、唯一写网关、权限矩阵、路由与工具。
5. 本文 —— 文件地图、定向测试、配置分层、交接清单。

> 02 的 §5–§10 是视图口径、测试记录、里程碑与偏差记录，按需查，不要一次读完。

### 1.2 30 秒架构

```text
DSH 插件双半
├── host  lib/index.js ── settings → 三个 Store/Service → /ptw 路由（UI）+ ptw_* 工具（AI）
│    core/  纯函数：contract / grammar / derive / validate / window（三个域各一套）
│    host/  settings / writer / gateway / store / service / routes / tools（三个域各一套）
└── client  lib/client.js ── 手写 lazy-CJS 原生 React，无构建；侧栏「任务工作台」主面板

数据真源  $DSH_HOME/task-workbench/data（Markdown；不进 Git）
插件状态  $DSH_HOME/task-workbench/（settings.json / ids.json / idea-ids.json / writes.log）
```

- 三个数据域：任务（`TaskService` + `ptw_*`）、想法（`IdeaService` + `ptw_idea_*`）、复盘（`ReviewService` + `ptw_review_*` 只读）。
- **唯一写路径**：UI 与 AI → 各自 service → `WriteGateway`（串行队列 / `baseHash` / 写前备份 / 回读 / 审计）。不允许第二条写路径。
- **人机边界**：任务完成/撤销、想法状态流转、复盘正文 = **仅人**；AI 没有写工具，service 对非 user actor 兜底 `permission-denied`。
- 数据根与安装形态解耦（`link:` / 本地目录 / tarball / npm 包写同一处），升级重装不丢数据。

### 1.4 红线（违反即返工）

- 不新增第二条写路径；不让 AI 写人专有动作；失败不假装成功。
- 自动化测试只碰 `os.tmpdir()` 临时数据根；绝不写真实 `data/` 或 `$DSH_HOME`。
- 不把 `data/`、`settings.json`、`writes.log`、token、本机绝对路径提交进 Git。
- 临时产物（浏览器日志、截图 probe、mock 稿）放 `test-tmp/` 或 `.playwright-mcp/`（均已 gitignore），交付前清掉；不要把临时文件留在仓库根目录。
- 不引入构建步骤、运行时依赖或新的配置框架；不扩大 V3.0 功能边界（超边界先讨论或另开版本）。
- 文档「写完」≠「已验证」；验收证据必须来自真实运行（测试输出、真机刷新/点击/截图）。

## 2. 日常操作流程（所有者视角）

### 2.1 平时：改完就用，不发版

1. 小步改代码 → 按 §3/§4 跑**定向测试** → host 关/开插件组件（或重启 App）；client 刷新页面。
2. 自用确认没问题 → 本地 `git commit`（AI 可以提交；**不要 push**）。
3. 不动版本号，不碰 npm。

### 2.2 定期：攒一批可感知改动，再发版

1. 发版前跑一次全量 `npm run verify`（语法 + 89 用例）。
2. 按 [04 发布与更新](./04-发布与更新.md) 发版；也可用 `npm run release`（04 §2.0）一条命令完成：全量测试 + 打包校验 → 升版本 → push → npm publish → Release。
3. 是否要发版的判定：

| 改了什么 | 要发版吗 | 说明 |
|---|---|---|
| `docs/`、`AGENTS.md`、`CONTRIBUTING.md`、CI | 否 | 不进入 npm 包，GitHub 更新即可 |
| `README.md` / `README.zh-CN.md` / `LICENSE` | 一般否 | 会随 npm 包更新，但不影响功能；想让 npm 页面同步就随下次发版 |
| `lib/`、`skills/`、`locale/`、`icon.svg`、`cordis.patch.yml` | 是 | 用户装的是 npm 包，GitHub 更新不会自动到用户（patch 在 `package.json` 的 `files` 白名单里） |
| `package.json` 的分发字段（版本/engines/exports/files 等） | 是 | 影响安装与分发；`scripts` 等纯开发字段不影响安装 |

4. 市场条目一般不动；只有改名 / 换仓库 / 描述或图标变化才改（04 §2.6）。

### 2.3 每天、每周不用做的事

- 不用手动备份：每次写前自动备份，默认保留 7 天（`backupRetentionDays` 可配 1–90）。
- 不用手动清理 `data/`：任务按月分片、历史只读；想法与复盘单文件长期保留。
- 不用让 npm 版本追上每个提交：版本只在发版时升。

## 3. 测试纪律（默认定向，不做全面回归）

### 3.1 分层

| 层 | 内容 | 何时跑 |
|---|---|---|
| L0 语法 | `npm run check`（`node --check` 两个入口） | 每次改 `lib/` 后 |
| L1 定向 | 对应域的测试文件（§3.3 / §4） | 每次改完、提交前 |
| L2 全量 | `npm test`（89 用例，约 0.8s） | 发版前、跨域改动、CI |
| UI 验收 | 真机刷新/点击/截图 | 改 `lib/client.js` 或影响界面的接口 |

### 3.2 硬规则

- **默认定向**：改哪个域跑哪个域；通过即停，不为「保险」扩大范围。
- 全量**最多一次**；只在四种情况跑：① 发版前 ② 跨域共享代码（`gateway.js` / `writer.js` / `settings.js` / `lib/index.js` / 路由协议）③ 迁移或数据结构变更 ④ CI。跑前说明影响面与「定向为何不足」。
- **禁止**「顺便回归」；**禁止**代码没再变化时重复跑全量。
- 新增测试只在「修 bug 补回归」或「新增/修改数据契约字段」时加；不为覆盖率写测试，不为 UI 写 DOM 测试（用真机验收）。
- 慢用例/真实渲染默认不进自动化；当前没有此类用例。

### 3.3 常用命令

```bash
npm run check          # 语法（两个入口分别 node --check）
npm run test:task      # 任务：core + service + routes（33 个用例）
npm run test:idea      # 想法：core + service + routes + tools（27 个用例）
npm run test:review    # 复盘：core + service + routes + tools（24 个用例）
npm run test:cross     # wiring + settings + skills（5 个用例）
npm test               # 全量 89（只在 L2 场景跑）

# 更细：只跑某个用例组
node --test --test-name-pattern='review-window' tests/review-core.test.mjs
```

### 3.4 现状结论：是否过度测试？

- 现状：89 个用例、约 0.8s、三个域按 core → service → routes/tools 分层；**不算过度**。没有慢用例，断言集中在数据契约与用户可见行为（不锁 UI 内部结构）；service 与 routes/tools 的重复覆盖属于分层必要（前者测网关语义，后者测协议边界）。
- 真正要避免的不是用例数量，而是「小改动就全量」的习惯。**用例保留，执行按 §3.2**。
- 审计发现 2 处边缘重复：`idea-tools` 的「AI 改状态被拒」与 `idea-service` 同断言；`skills.test` 断言 SKILL.md 的具体文案（改说明文案会红）。保留不改——为删测试而改测试不值得，但要避免再新增同类断言。
- 功能层面当前没有过度开发证据：实现与 01/02 的「不做什么」一致。不要为了测试或「以后可能用」增加能力。

### 4.1 已知测试盲区（事实，不构成补测理由）

- `lib/client.js`（约 2200 行）没有自动化测试，只能真机验收；它内部还重复实现了部分列表/计数逻辑。
- 未覆盖的错误码：`queue-busy` / `timeout` / `id-exhausted` / `rollover-failed` / `backup-failed` / `write-failed` / `config-invalid`。
- 备份清理与 `backupRetentionDays` 的 1–90 clamp 未测；月切只覆盖 11→12。
- 任务 `## 任务` 重复区块、标题 >200、`format: 2`、闰年 2/29 未测。
- `/reload` 与 `locale/*.json` 无测试。
- 这些缺口只在对应行为被改动或出现 bug 时补回归；不要为「覆盖率好看」批量补测。

## 5. 配置文件分层

### 5.1 运行时与仓库配置（四层，已足够）

| 层 | 文件/位置 | 管什么 | 入库 | 改法 |
|---|---|---|---|---|
| L1 包与引擎 | `package.json` | 包名、版本、`engines`、`exports`、`files`、发布配置 | 是 | 改动即影响安装，需要发版 |
| L2 插件装配 | `cordis.patch.yml` + `package.json` 的 `dsh` 字段 | Host / Client 半如何被加载 | 是 | 改装配后真机重载验证 |
| L3 本机运行 | `$DSH_HOME/task-workbench/settings.json` + `ids.json` / `idea-ids.json` / `writes.log`；profile 的 `link:` | 数据根、备份保留天数、ID 水位、审计、本机安装路径 | **否** | 只改本机，不进仓库 |
| L4 协作/开发 | `.github/workflows/ci.yml`、`.gitignore`、`AGENTS.md`、`CONTRIBUTING.md`、`docs/` | CI、忽略规则、Agent 边界、文档 | 是 | 改完按本文 §6 验收 |

### 5.2 运行时取值优先级（`lib/host/settings.js`）

1. `DSH_HOME` 环境变量决定**状态目录**（默认 `~/.dsh`）→ `$DSH_HOME/task-workbench/`。
2. `settings.json` 的 `dataRoot` 覆盖**数据根**（缺省 = 状态目录下的 `data`；相对路径按进程 cwd 解析）。
3. `settings.json` 的 `backupRetentionDays`：默认 7，夹在 1–90。
4. 不存在仓库级 / 项目级运行时配置，也没有直接改 `dataRoot` 的环境变量第二入口——避免第二真源。

> 现状：本机 `settings.json` 的 `dataRoot` 指向仓库内 `data/`（本地开发形态，已 gitignore）。

### 5.3 Agent 指令分层

- 全局 `~/.dsh/AGENTS.md`（本机所有工作区通用的行为契约）→ 项目 `AGENTS.md`（本仓硬边界）→ 当前对话/任务指令（最具体，优先）。
- Agent 文件只放「每次都要遵守的边界」；细节放本文或 02；不复制大段规则，避免多处同步。

### 5.4 不要做成配置的东西

- 只有一个用户、一个数据根时，不引入 `.env`、多环境配置文件或配置加载库。
- 不把数据根做成命令行临时参数；需要换路径就改 `settings.json` 后重载插件。
- 不把 token、本机绝对路径、个人数据写进仓库配置。

## 6. 交接与验收清单

### 6.1 每次改动完成后

- [ ] 改的是授权范围，没有新增边界外能力。
- [ ] `npm run check` 通过；按 §4 跑对应定向测试，记录命令与结果。
- [ ] 涉及 host：关/开插件组件或重启后复验；涉及 client：刷新后复验（必要时截图到 `docs/acceptance/`）。
- [ ] 同步更新 02（契约/实现变化）与本文或 README（流程变化）；链接可点。
- [ ] `git status` 只含本次改动；本地 commit（不 push）。

### 6.2 发版额外（以 04 为准）

- [ ] `npm run verify` 全量通过；`npm run pack:check` 校验 `files` 白名单（必需文件都在包里）。
- [ ] 版本号按语义化升；`git push origin main --follow-tags`；`npm publish`；GitHub Release。
- [ ] 发版后用 npm 安装路径在真机复验一次（证明用户拿到的是新版本）。

### 6.3 回报格式

- 区分**已实现 / 已验证 / 未完成**；写明运行命令与结果、未验证项及原因、是否触碰真实数据/进程/收费服务。
